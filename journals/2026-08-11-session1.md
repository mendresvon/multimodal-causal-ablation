### 3. Experimental Execution & Parameters

The diagnosis proceeded as a front-end sweep, then a matched-pair argument, then a control.

**The matched-pair argument.** `src/datasets.py` ships two commented-out lines in `IEMOCAP.__getitem__`:

```python
# waveform, sr = torchaudio.load(os.path.join(sample_folder, f'audio_16000.wav'))
# specgram = torchaudio.transforms.MelSpectrogram(sample_rate=sr, win_length=int(float(sr) / 16000 * 400))(waveform).unsqueeze(0)
```

and two live lines that load `audio.wav` and scale `win_length` by `sr / 44100`. `torch.stft` requires `0 < win_length <= n_fft`, and `MelSpectrogram`'s default is `n_fft=400`. Therefore `win_length = int(sr / 16000 * 400)` is only *expressible* when `sr <= 16000`. The commented `win_length` and the commented `audio_16000.wav` load cannot be separated: whoever wrote them wrote them as a pair, and the 16 kHz route is the one that yields the training-era `win_length = 400`. The live 44100 Hz route yields `int(44100 / 44100 * 400) = 400` as well — but on the *wrong waveform*, and pairing the 16 kHz clip with the live line would give `int(16000 / 44100 * 400) = 145`, which is not the training window. That is why the rebind pins the window explicitly and asserts it.

**The fix.** Rather than wait on Drive sync (section 5), `IEMOCAP.__getitem__` and `IEMOCAP.sample_imgs_by_interval` were rebound in the runtime, inside the "Day 0: Canonical Data Load + Halting Fidelity Gate" cell, after `importlib.reload`. The rebind prefers `audio_16000.wav`, resamples `audio.wav` only if the 16 kHz clip is absent, and pins `win_length` to 400. It proves it took by **object identity** (`is`), not by `inspect.getsource`, which can raise for a function defined in a notebook cell — a false halt there would be indistinguishable from a real one.

The block is preserved verbatim at [`docs/recovered/2026-08-11-session1-audio-rebind.py`](../docs/recovered/2026-08-11-session1-audio-rebind.py).

**The 16 kHz corpus.** `RML_RAW_PROCESSED_Face.tar.gz` — the tarball extracted inside the runtime — carries no `audio_16000.wav`. The real 16 kHz clips were therefore shipped separately as `data_bundle/RML_audio16k_all720.tar` and overlaid over the extracted corpus in Day 0 step 0. Session 1's step 0 printed:

```
16 kHz audio overlaid: 720 files, all 16000 Hz, 1 channel(s), 32-bit format tag 3
```

Format tag 3 is IEEE float, which the stdlib `wave` module refuses; the headers were parsed directly with `struct.unpack('<HHIIHH', head[20:36])`.

**Frame counting.** `sample_imgs_by_interval` was changed from `len(glob(folder/*)) - 2` to `len(glob(folder/image_*.jpg))`. The `- 2` was exact only on the training machine, where every folder held both `audio.wav` and `audio_16000.wav`; under the runtime-extraction route each folder has one non-image member, not two. This change is the one part of session 1 that survives in version control (`Model/Dig-Data_Model-Main/src/datasets.py:294`) and is recorded in ADR 0005 Decision 4 under "Superseded 2026-08-11".

One test sample is 0.694 pp of 144, so `-1.39 pp` is exactly two samples; this arithmetic was used throughout to tell real drift from rounding.

**This retires ADR 0004's claim that `audio_16000.wav` is "read by no code path."** That sentence was the exact wrong premise behind the gate failure. It is true of the shipped `src/datasets.py` and false of the configuration that reproduces the training log.

### 5. Roadblocks, Failure Modes & Debugging Log

**The Google Drive upload stall.** Midway through, Colab kept executing the *old* loader after the local file had been fixed. The deployed revision was identified byte-exactly rather than guessed: Colab was reading a 26950-byte `src/datasets.py`, and commit `bc5bb91` with the frame-count fix applied and nothing else reconstructs to exactly 26950 bytes (27005 − 55 = 26950). That pinned the difference to `IEMOCAP.__getitem__` alone and justified rebinding only the two methods rather than shipping a whole module. Recorded as memory `drive-upload-stall-bypass.md`.

**An AppleDouble sidecar incident.** macOS Finder wrote `._`-prefixed files into the corpus; those names match `image_*.jpg` and inflate the frame count silently. This is the same hazard class as the stray `.DS_Store` in ADR 0005 Decision 4 and is why the Day 0 integrity gate replicates the sampler byte-for-byte before any model loads.

### 6. Interpretability Retrospective

The gate did its job. A 20-point accuracy hole caused by a silently wrong audio sample rate is exactly the failure class the halting gate exists to catch: no exception, no warning, just a model quietly attending to a spectrogram it was never trained on. Had the gate been a printed warning rather than an `AssertionError`, Weeks 1–4 would have run to completion on a broken front end and produced a full set of plausible, publishable, wrong numbers.

The second lesson is about evidence. The fix lived in the notebook and in the runtime, not in `src/datasets.py`, and it was never pushed. When those commits were destroyed, the *only* surviving trace inside the repository was one row in `journals/README.md` — and a later session, reasoning carefully from `git log -S` over the surviving history, concluded that row was unsupported and told the next reader to treat the 16 kHz tar as unused. The reasoning was sound; the evidence base had a hole in it that the method could not see. See the counter-erratum on that row.
