### 4. Empirical Findings & Data Links

**`data/` is empty by design, not by accident.** `.gitignore` excludes everything under `data/` except `data/README.md`, and the actual RML corpus lives at `Model/Dig-Data_Model-Main/data/BIG_DATA_RAW_PROCESSED_FACE/` (720 folders, verified present and complete in session 2), which is separately excluded and untouched. Nothing to fix.

**`journals/` is not disorganized — it's a flat log with an index, per ADR 0002 §2.** `journals/README.md` already has one row per entry naming its date, protocol stage, status, and a one-line summary, and `journals/GUIDELINES.md` fixes the `YYYY-MM-DD[-sessionN].md` naming scheme as the convention. Grouping into subfolders (e.g., by week) would require rewriting every internal cross-reference in past journal entries — which are first-person dated records of what happened at the time and should not be retroactively edited — for a purely cosmetic gain. I left the structure as-is.

**Real empty directories found:** `results/`, `figures/`, `checkpoints/activations/`. All three are expected to be empty right now — they're write targets for the Colab run (Day 0 fidelity numbers, Week 1 activation cache, any plots), not leftover clutter. `results/` and `figures/` are Git-tracked per ADR 0002 §1 ("lightweight results" and "figures" are explicitly named as tracked); `checkpoints/activations/` is gitignored. None of the three should be deleted.

**The two `0003`-numbered ADRs are a numbering collision, not duplicate content, and ADR 0004 already resolved the ambiguity in writing.** `0003-targeting-cls-tokens-for-ablation.md` and `0003-causal-ablation-v2-methodology-remediation.md` cover different decisions (CLS-token vs. FFN-output targeting; v2 pipeline remediation) that happened to get the same sequence number. ADR 0004's Status line already states it supersedes both and retains them "for historical record." Both filenames are referenced by exact name from `journals/2026-08-07.md` and `journals/2026-08-09.md` — past, dated, first-person entries — so renaming either file would break those references for no benefit, since the ADR-level ambiguity is already resolved. **My call: keep both, keep the names as-is.** Deleting an ADR the project's own most recent ADR explicitly chose to retain would be reversing a decision that was made two commits ago with more context than I have right now, over an away user's back, for a cosmetic win.

**The retracted `multimodal-causal-ablation.ipynb` and `-v2.ipynb` are cited by name from `README.md` line 23 as the specific artifacts ADR 0004 retracted.** Deleting them would sever that citation and remove the actual retracted evidence, leaving "results are retracted" as an unverifiable claim instead of a diffable one. Both are small (<230 KB) and already Git-tracked, so they cost nothing to keep. **My call: keep.**

**Two items were pure junk with no documentation value, so I removed them without ceremony:**
- `.DS_Store` at repo root and `src/.DS_Store` — Finder droppings, already covered by `.gitignore`, and the exact hazard class flagged in ADR 0005 §4 (a stray `.DS_Store` inside an RML sample folder silently shifts the frame count; these two were outside any sampled folder, so harmless, but there's no reason to keep them lying around this Drive-synced directory).
- The local branch `harden/v3-preflight` — session 2's work landed on it, and `git rev-parse` showed `main`, `origin/main`, and this branch all pointing at the identical commit `87d45dc`. It had already been fast-forward-merged and pushed; the pointer was inert. `git branch -d` (not `-D`) only deletes a branch Git confirms is fully merged, so this was a no-risk cleanup.

### 6. Interpretability Retrospective

The instruction to "optimize" a directory implicitly asks a question this project keeps running into at every layer: does removing something make the record clearer, or does it just make the file tree shorter? ADR 0004 exists because a prior session silently substituted the wrong `meta.pkl` and nothing caught it. The two `0003` ADRs and the retracted `v1`/`v2` notebooks are the opposite failure mode done right — something went wrong, and instead of deleting the evidence, the project kept it and wrote down, in the next ADR, exactly why it no longer applies. Deleting them now to make `docs/adr/` look tidier would trade a real audit trail for a shorter `ls` output. I only removed the two things that had zero documentation value and zero references — `.DS_Store` files and an already-merged branch pointer. Everything else that looked messy in the file tree turned out to be either gitignored-and-expected-empty, or a design decision already made and written down by an earlier ADR. The actual finding of this session is closer to "no, don't delete that" than "here's what I deleted."
