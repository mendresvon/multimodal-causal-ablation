### 4. Empirical Findings & Data Links

**The checkpoints are correct — this was never the bug.** SHA-256 of `checkpoints/base_model.pt` = `565bc220...`, matching `RML_origin/mme2e_tav_0.6724_..._seed0.pt` exactly. Same for `finetuned_model.pt` against `RML_finetune/mme2e_tav_0.7586_..._seed0.pt`.

**The `.pt` filenames encode validation-set metrics, not test accuracy — this caused a false alarm in two places.** The training log `Final_result/Origin_training/wrong_stat/RML_finetune/mme2e_tav_0.7586_..._seed0.txt` shows, at the epoch the checkpoint was saved:
```
Valid    0.7586    0.7611       0.7708  0.7627
Test     0.7986    0.7986       0.7982  0.7968
=== Best performance ===
Test (15)  0.798611  0.798611     0.798164  0.79676
```
Test accuracy at that epoch is 79.86%, which is exactly Figure 4.3's published fine-tuned-model accuracy for RML. The base model's log shows the same pattern: `Test (29) 0.763889` = 76.39%, exactly matching Figure 4.3's base-model accuracy. So `target_base=76.39` / `target_ft=79.86`, hardcoded in v2's Day 0 cell, were correct all along — nobody had connected that the checkpoint filenames themselves report a *different* metric (validation, not test).

**Checkpoint loading is clean.** Reimplementing every pure-PyTorch submodule and diffing `state_dict()` keys against the checkpoint gave 265/265 matches for the non-text/non-face submodules and 25/25 for ALBERT (one harmless extra buffer, `T.albert.embeddings.position_ids`, which is a non-persistent, non-learned position index in newer `transformers` versions). Zero missing keys, zero shape mismatches, anywhere in the classification-relevant path. The `strict=False` in the notebook's `load_state_dict` calls was never silently dropping weights.

**The ablation hook target is correct.** `model.a_transformer(specs, spec_lens, get_cls=True)` returns `inputs[0]` from `WrappedTransformerEncoder.forward` — literally the CLS-token output, already 2D `[B, 64]`, which feeds directly into `a_out` and then the fusion sum. `docs/adr/0003-targeting-cls-tokens-for-ablation.md`'s concern (that "FFN output" in the protocol meant something different from the CLS representation) is a non-issue: there is no separate FFN layer to distinguish. `a_transformer`'s hooked output *is* the tensor the protocol and the paper mean.

**The actual bug: wrong data source.** `main.py`'s `get_dataset_iemocap` (the function used for every dataset including RML) reads from `BIG_DATA_RAW_PROCESSED_FACE/meta_one_hot_label_six_categories.pkl` — a single merged folder covering all six datasets, with the per-dataset split selected only by which split-file name is read. The v2 notebook instead reads `Model/Dig-Data_Model-Main/data/RML_RAW_PROCESSED_Face/meta.pkl`. I listed `RML_RAW_PROCESSED_Face.tar.gz`'s contents on the handover drive and found no `meta.pkl` anywhere in it — only per-utterance `image_*.jpg` and `audio.wav` files. That `meta.pkl` was fabricated by an earlier agent session (referenced obliquely in `docs/adr/0003-targeting-cls-tokens-for-ablation.md` and the 2026-08-04/05 journal entries as a preprocessing convenience), not sourced from the canonical merged corpus. Its text field, label encoding, or sample set may not match what the checkpoints were actually trained/evaluated against. This is sufficient on its own to explain a same-checkpoint accuracy drop from 76.39%/79.86% down to the observed 56.94%/47.92% (with fine-tuned below base, which the true numbers never show).

**Split-count confirmation.** The training log states `Train samples = 518`, `Valid samples = 58`, `Test samples = 144` — matching Table 4.2 of the thesis exactly. v2's Days 1–2 cell concatenated `train_ids + valid_ids` and got 576 after filtering to its fabricated `meta.pkl`, not 518+58=576... actually that arithmetic does match (518+58=576), so the *count* was coincidentally right; the *content* (whether those are the correct 576 utterances with correct labels/text) is what's unverified given the fabricated meta.

**Dominant modality is a genuine near-tie, not a clean win.** The thesis states directly: "In the RML model, the dominant modality is text and audio" (§4.4, discussing Figure 4.34), and separately that the best-performing modality combination for RML is audio+video. `docs/adr/0001-causal-validation-methodology.md`'s tie-break (target Audio 64-d when Text/Audio parity is within 5%) is consistent with the thesis's own framing, not a shortcut invented for this project. The IEEE paper's Section VI-D method text says we hook "the FFN output of the dominant modality" — the write-up needs to say plainly that Audio was chosen under a text/audio near-tie via the dimension-invariant `mean(|phi|)` metric, not present Audio as an unambiguous winner.

### 6. Interpretability Retrospective

Both prior failures trace back to a single break in provenance, not a statistical subtlety. Every ADR and audit written on 2026-08-04 through 2026-08-07 — the SHAP formula fix, the leakage-free 80/20 split, the epsilon-screened retention taxonomy — was a real, defensible fix to a real problem, but all of it was computed on top of a model whose predictions never matched the checkpoint it claimed to be evaluating. The ε=0.05 screen in particular was solving a symptom (division-by-zero and negative ratios) produced by a broken harness, not a genuine statistical edge case. None of that methodology work was wasted — the thresholds and taxonomy are still the right design — but none of the numbers it was run on mean anything.

The most instructive artifact is the "class permutation solver" in v2's Day 0 cell: when the measured accuracy didn't match the target, instead of treating that as a stop signal, someone (an earlier agent session) wrote code to search all 720 label permutations for one that would make the numbers match, and when even that failed, silently fell back to whatever permutation looked best and continued the entire experiment. That is fitting the evaluation to the answer. A fidelity check that can be satisfied by search is not a fidelity check.

**Blocking check resolved (same session, later):** `tar -tzf` on the full 42GB archive was too slow to be practical (Python `tarfile` iteration and BSD `tar -tzf` both took an impractically long time; the first `tar -tzf | grep -i meta` background job alone ran for roughly two hours before finishing). Switched to `gzip -dc archive | grep -a -o -m1 <filename>` for existence, then `gzip -dc archive | tar -xf - -O <path>` to pull just the one member — both far faster since they avoid per-entry object construction and stop as soon as the target is found. Confirmed `BIG_DATA_RAW_PROCESSED_FACE/meta_one_hot_label_six_categories.pkl` exists (9.3 MB, 63,723 total keys across all six datasets) and that **all 518 train + 58 valid + 144 test RML split IDs are present as keys**, zero missing. The one-hot label encoding inside (`[0,0,0,0,1,0]` for `sad`, `[1,0,0,0,0,0]` for `ang`, etc.) matches the fixed `EMO_DICT` ordering already hardcoded in `multimodal-causal-ablation-v3.ipynb` exactly, so no changes to the notebook's data-loading cell were needed.
